ABOUT THE NAME

AI-DevContinuumとは

AI-DevContinuum（エーアイ・デブ・コンティニュアム）は、AI × Development × Continuumから生まれた名前です。

AI-DevContinuumが目指すのは、単に開発工程を管理することではありません。

要求ヒアリングから要件定義、設計、実装、テスト、品質分析までをAIでつなぎ、
そこで生まれたレビュー・テスト・障害・品質の知見を次の開発へ還元する。

開発するたびに企業の知識と品質が蓄積され、AIによる支援も継続的に進化していく。

開発を「点」ではなく「連続する知の循環」として捉える。

それが、AI-DevContinuumという名前に込めた思想です。

BACKGROUND

AIで自動化・効率化を図りたいシステム開発会社向け

パッケージ製品への乗り換えではなく、いまの開発フローにAIを組み込んで効率化したい会社に向いています。PM・SE・QAがそれぞれ実務で抱えている悩みに、AI-DevContinuumの機能が直接応えます。

01
開発ドキュメント作成に時間がかかる
要件定義書・設計書・テスト仕様書などを毎回ゼロから作成しており、ドキュメント作成が開発者の大きな負担になっている。
→ AIによる成果物生成（AI下書き→人間承認）
02
レビュー品質が属人化している
ベテランの経験や勘に頼ったレビューになっており、担当者によって品質にばらつきがある。過去の指摘が次の案件に活かされない。
→ AIレビュー＋品質フィードバックで観点を蓄積・自動反映
03
要求・設計・テストの漏れを防ぎきれない
要求と設計、テストケースの紐付けをExcelなどで管理しており、実装漏れ・テスト漏れ・対応関係の確認に手間がかかる。
→ トレーサビリティ＋テストマトリクス＋カバレッジ
04

不具合、リスク、テスト進捗、カバレッジなどの情報が各所に分散し、PMが「今どこに問題があるのか」をリアルタイムに把握しにくい。
→ 品質ダッシュボードで一元把握（WBS・進捗管理は専用画面で提供、ダッシュボード統合は今後）

V字モデル×AI支援×品質フィードバックの関係

開発モデルにはV字モデルを採用し、要件定義⇔システムテスト・基本設計⇔結合テスト・詳細設計⇔単体テストが対応関係（トレーサビリティ）を保ちます。 実装・テストで得られた不具合・レビュー・実行結果はAI品質分析にフィードバックされ、そこで生まれたレビュー観点は次のプロジェクトのAIレビュー精度向上として還元されます。

機能マップ。AI支援・V字モデル・品質フィードバックループが1つの構造でつながっている

なぜ全部を1つの基盤にしたのか

全部を1つの基盤にするかどうかは、設計の初期段階で実際に比較検討したポイントです。 比較したのは「ドキュメント生成ツール＋品質管理SaaS＋コードレビューツールの併用案」と「単一基盤案」の2つです。 併用案にも利点はあります。専門特化している分機能は深く、乗り換えコストも個別に小さく済みます。

ただし併用案では、要求・設計・テスト・レビューの情報がツールごとに別々のデータへ分断されるため、 REQ-IDによる要求⇔設計⇔テストの対応関係を、ツールをまたいで維持できません。 要求が変わった影響がどのテストケースに及ぶか、レビューで指摘された観点が次のAIレビューに反映されるか、といった連携も、 情報が分断されている分だけ、個別のインポート・エクスポート作業に頼ることになります。

そのため単一基盤案を採りました。要求から品質分析までを同じREQ-IDで一元管理でき、不具合分析で見つかったレビュー観点の抜けはそのまま次のAIレビューへ自動反映されます。

基盤をまたぐと、対応関係の維持と情報連携が二重になります。作るときは大差なくても、案件を重ねてから効いてきます。

DEVELOPMENT PROCESS

開発プロセスの機能

要求ヒアリングから実装・単体テスト・コードレビューまで、各工程は「AIが下書きする」「人間が承認する」の順で進みます。

要求管理ヒアリング・要求抽出

会話ログや議事録をAIが読み、機能要求・画面・不明点を抽出します（機能要求はREQ-ID単位で管理されます）。抽出結果は要件定義書の元データとなり、その後の生成・レビュー・承認の過程で人間が内容を確認します。

設計・仕様要件定義書〜結合テスト仕様書のAIレビュー

要件定義書はヒアリング内容、基本設計書は承認済みの要件定義書、詳細設計書は承認済みの基本設計書というように、各成果物は直前に承認された成果物の内容を踏まえてAIが生成します。生成後は、成果物の種類ごとに定めた5つの観点（例:要件定義書なら完全性・一貫性・明確性・実現可能性・トレーサビリティ）でAIがレビューし、スコアと具体的な指摘を返します。承認するかどうかは人間が決めます。章立てや必須項目は企業独自のテンプレートとして登録でき、承認済みの成果物はMarkdown・Word・Excelの3形式で出力できます。

要件定義書のAIレビュー結果（実際の案件データ）。観点別スコアと具体的な指摘、承認履歴を1画面で確認できる

実装AIコード生成

設計が承認されたら、次は実装です。実装は白紙から書き起こすのではなく、既存のソースコードに手を加える形で進みます。起点は2つあります。承認済みの詳細設計書をAIに渡し、変更対象の特定から提案までを任せる方法と、人が対象ファイル・変更内容を指定する方法です。後者は次の順で進めます。

  1. 対象ファイルを選ぶ — 登録済みリポジトリの既存ファイル一覧から、変更したいファイルを人が選択します
  2. 変更内容を日本語で伝える — 「SLA期限を2時間から1時間に短縮する」のように、依頼したい内容を記述します
  3. AIが差分を提案 — 何を変え、何を変えていないかの判断根拠つきで、コードの修正案を提案します
  4. 検証して承認 — サンドボックスでテストを自動実行し、合格を確認したうえで人が承認したものだけがリポジトリに反映されます（却下も可能）

どちらの起点でも、検証・承認のステップは共通です。対応言語はPython・Node.js・Go・Java・C#（.NET）・C/C++の6言語に標準対応しています。

AIコード生成の提案画面。変更範囲を絞り込んだ根拠をAI自身が説明する（実際の生成結果）

実装単体テスト自動生成 / 詳細設計書からのテストケース抽出

コードから単体テストをAIに書かせるだけでなく、詳細設計書の最新版からテストケースを抽出することもできます（承認前のドラフト段階でも抽出可能です）。前提条件・手順・期待結果がケースごとに整理され、そのままテストコード生成に進めます。

詳細設計書から抽出したテストケース（実際の案件、23件）。ケースごとにテストコード生成へ進める

コードレビューレビューエンジンの選択（Claude CLI / Codex CLI）

自己参照のコードレビューだけでなく、クライアント案件のコード生成・単体テスト生成でも、Claude CLIに加えてOpenAI Codex CLIを選べます。1つのコードを2つのAIの目でダブルチェックできます。

コードレビューのエンジン選択画面。Claude CLI / Codex CLIを切り替えて実行できる

HOW WE BUILD

AIとどこまで一緒に作るかを決めておく

「AIが自動でやります」とだけ言っても、現場のPM・エンジニアには何が変わるのか伝わりません。工程ごとに「人がやること」と「AIがやること」を分けています。

工程人がやることAIがやること
ヒアリング 会話・議事録の記録、内容の確認 機能要求・画面・不明点の抽出
要件定義書〜結合テスト仕様書 本文の確認、承認 / 差し戻し ドラフト生成、AIレビュー
コード変更・単体テスト 変更依頼の記述、適用の承認 コード生成、サンドボックスでの検証
不具合分析 分類結果の確認・確定 根本原因の分類、類似不具合の検索
リリース判断 最終的な進行可否の決定 リスク予測、品質スコア算出、所見文生成

確定させない工程を決めておく

成果物の下書きも、コードの変更案も、AIが作れます。一方で、成果物の承認・コード変更の適用・リリースの可否は、常に人が持ちます。 品質スコアやリスクの数値も決められた計算式でしか算出せず、AIに点数を作らせることはありません。

この線引きを最初に決めておくと、AIの提案が増えても「これは人が見なくていいのか」で迷いません。

QUALITY ANALYSIS

品質分析・管理の機能

「見える化 → 不具合分析 → AI予測 → AI評価 → 品質フィードバック」の5層で品質を管理します。数値の算出はすべて決定論的なロジックで行い、AIは判断材料の説明や所見文だけを書きます。

ガバナンスデータ取り込み・機能マスタ

CSV・JUnit形式のテスト結果やGit連携から実績データを取り込み、機能マスタを整備します。ここで取り込んだ実績が、この先の不具合分析・リスク予測の元データになります。

データ取り込み画面。外部の実績データを機能マスタに紐付けて取り込む

見える化品質ダッシュボード

不具合件数・原因内訳・カバレッジなど、案件の品質状態をKPIカードとグラフで一望できます。集計はすべて実データからの機械的な計算です。

品質ダッシュボード（実際の案件データ）

不具合分析不具合分析・根本原因分析

登録された不具合をAIが根本原因・混入工程ごとに分類し、原因カテゴリの構成比や機能とのクロス集計まで自動で作ります（検出工程は取り込んだ実績データの値をそのまま使用）。分類結果の確定は人間が行います。

AI予測再発リスクマップ（7要素）

不具合密度だけでなく、直近の変更量・カバレッジ不足・変更頻度・類似案件・レビュー指摘の集中度・要求変更の多さまで加味してリスクを算出します。重みは画面から調整でき、内訳（生値と相対値）を必ず併記します。

再発リスクマップ（実際の案件データ）。7要素の内訳から総合リスクスコアを算出する

AI評価テスト十分性評価・テストマトリクス

要求とテストケースの紐付け状況から、未検証の要求や不足しているテスト種別（異常系・境界値など）を検出します。要求×テストケースの対応表では、空白セルからそのままAIにテストケース起案を依頼できます（機能×テストケースの対応表は件数確認用です）。

品質フィードバック品質スコア・品質ゲート

要求カバレッジ・異常系比率・出荷前検出率・手戻り率・品質ゲート通過率を重み付け合算して品質スコアを算出します。品質ゲートは結合テストへ進む条件などを判定し、未達でも理由を記録すれば人間が上書き通過できます。数値そのものはAIに作らせません。

トレーサビリティトレーサビリティ・ナレッジ管理

要求⇔設計⇔テストの対応関係をREQ-IDで追跡できます。改善提案はレビュー観点として昇格させ、以降のAIレビューへ自動で反映する組織学習の仕組みも備えています。

SECURITY & GOVERNANCE

AIに何を渡すか、誰が何を承認したかを、常に管理下に置く

AIを業務に組み込むうえで避けられない不安に、機能として答えます。「便利だが何をしているか分からない」状態にはしません。

送信前マスキング
個人情報・秘密情報の自動マスキング
氏名・メールアドレス・電話番号・IPアドレス・APIキー等をAIへ送信する前に検出し、トークンへ置換します（氏名は登録済みの人名辞書との照合方式です）。マスキング規則の不備を検知した場合は送信そのものを中止します（fail closed）。
送信前プレビュー
実際に送信される内容を画面で確認
マスキング適用後、AIへ実際に送信される文面をそのまま画面上で確認できます。「何が送られているか分からない」状態を防ぎます。
監査ログ
AI呼び出しの全件記録
誰が・いつ・何の目的でAIを呼び出したかを記録します。プロンプト本文は保存せずハッシュのみを残し、ログ自体が新たな機密情報の保管場所にならないようにしています。
サンドボックス検証
コード変更は隔離環境で検証してから反映
AIが提案したコード変更は、隔離したコピー上でテストを自動実行し合格を確認したうえで、人間が承認した場合のみ実リポジトリへ反映します。
権限管理
役割ベースのアクセス制御
管理者・オーナー・レビュアー・メンバーの役割ごとに、承認・設定変更・コード適用などの操作権限を分けています。
決定論的スコア
数値はAIに作らせない
品質スコア・リスクスコア・進捗率などは全て決められた計算式で算出します。AIが担うのは所見文の説明のみで、数値そのものを提案・修正することはありません。

FUTURE

今後実装していく機能

以下はAI-DevContinuum導入時に対応を予定している機能です。カスタマイズ費用は、導入費用・ライセンス費用に含まれています。

01
夜間の自動テスト実行＋結果通知（CI/CD連携）
現状、テストはサンドボックス環境で人が「検証」「採用」を押した時だけ実行されます。決まった時刻にGitHub上の最新コードを取り込み、蓄積済みのテストケースを自動実行して結果を通知する仕組みを構想しています。
02
過去成果物・レビュー履歴のRAG構築
これまで蓄積した設計書・レビュー指摘・不具合データを検索可能な形にし、AI生成・AIレビューの根拠として参照できるようにします。
03
企業専用AIレビュアー（組織学習のさらなる強化）
現状も、改善提案をレビュー観点として昇格させ以降のAIレビューへ自動反映する仕組みは稼働しています。これに加えて過去の全成果物・レビュー履歴をRAGで検索・参照できるようにし、組織固有の「暗黙のルール」を踏まえたレビューへ発展させます。
04
AI PMの遅延予測・ダッシュボード統合
要件定義書からAIがWBSのたたき台（タスク・関連REQ-ID・見積工数）を自動生成し、実績工数の入力に応じて工数加重の進捗率を算出する機能は実装済みです（案件ごとのWBS画面で利用できます）。現状の遅延の目安は予実の単純な比率であり、統計的な遅延予測やAIによる対応案の自動提案、メインダッシュボードへの統合は今後の拡張です。
05
開発標準エンジンの準拠率数値化
コーディング規約や社内ルールをAI-DevContinuumに取り込み、コード生成・レビューの判断材料として使う仕組みは実装済みです。今後は、自己参照コードレビューで培った「確定済みの設計判断と照合する」仕組みも組み合わせ、規約への準拠率を数値化していきます。
06
AI変更管理（影響分析→修正案自動生成）
要求変更時の影響範囲分析（実装済み）から一歩進め、影響を受ける設計書・コードの修正案までAIに起案させます。
07
さらなる対応プログラミング言語の追加
既定言語としてPython・Node.js・Go・Java・C#（.NET）・C/C++の6言語に対応済みで、それぞれに既定のビルド・テストコマンドを内蔵しています。今後はさらに対応言語を広げ、言語ごとの静的解析・カバレッジ計測との連携を強化していきます。
08
製品バリエーション管理（Feature / Option管理）
車種×グレード×オプションのように、製品構成の組み合わせごとに必要な要求・設計・テストが変わる領域に対応します。構成を選択すると対象の要求・設計・テストをAIが特定し、構成変更時の影響範囲も分析します。製造業のPLM的な構成管理と要求・設計・テストをAIでつなぐ構想です。
09
Compliance機能（規制対応支援の強化）
電子承認・変更履歴・監査ログ・承認済み成果物の改ざん防止など、規格対応に必要となりやすい記録・追跡の仕組みを強化し、規格別チェックリストやAIによるコンプライアンスチェックまで対応する構想です。特定規格（ISO 26262等）の認証取得を意味するものではなく、対応を支援する基盤機能として位置づけます。

統合開発管理ツールは要求・構成・規制対応まで含めた「守りの厳格さ」に強みがあり、規制産業や大規模組織での実績が豊富です。一方でライセンスは1ユーザーあたり年間数万円〜十数万円規模になることが多く、大規模導入では総額が数千万円規模に達することも珍しくありません。AI-DevContinuumは、AIによる下書き生成・レビュー・品質分析・ナレッジ蓄積を核に据え、軽量に立ち上げて自社の開発フローに合わせて拡張していく方向性の製品です。

FAQ

よくある質問

導入をご検討いただく際によくいただく質問です。ここに無い点は無料相談で直接お尋ねください。

既存の開発フローに途中から組み込めますか？

はい。全工程を一度に導入する必要はありません。要求定義・設計だけといった一部工程からの導入も可能で、Phase 1・2だけ動かして効果を見てから段階的なカスタマイズにも対応させていただきます。

対応しているプログラミング言語は？

既定言語としてPython・Node.js・Go・Java・C#（.NET）・C/C++の6言語に対応しています。それ以外の言語を使う場合は「その他」を選び、テストコマンドをご自身で入力していただくことでご利用いただけます（既定言語のような組み込みのテストコマンドは用意されていません）。

AIが生成した成果物やコードは、そのまま本番に反映されますか？

いいえ。AIが作るのは常に下書き・提案までです。成果物の承認・コード変更の適用・リリースの可否は必ず人間が判断します。

機密情報・個人情報の扱いは大丈夫ですか？

AIへ送信する前に、氏名・メールアドレス・電話番号・APIキー等を自動マスキングします。マスキング規則に不備を検知した場合は送信自体を中止します。詳しくは上記「セキュリティ・ガバナンス」をご覧ください。

導入までどれくらいかかりますか？

標準導入期間は6カ月を目安としています（導入・環境構築2カ月＋AIチューニング4カ月）。対象工程や案件規模、カスタマイズ範囲によって変動します。詳しくは「料金の目安」をご覧ください。

既存の他社ツール（要求管理・品質管理ツール等）からの移行は可能ですか？

現状、既存ツールからの自動移行機能はありません。導入時のヒアリングで現在お使いのツール・データ形式を伺い、移行方法を個別にご相談させていただきます。
